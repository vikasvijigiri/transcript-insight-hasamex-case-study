# Security checklist

Compiled 2026-09-22. This is the *cross-cutting* security audit — CORS, CSP, rate limiting, dependency scanning, XSS, OWASP API Top 10, and env-var handling were already covered in the frontend/backend checklists and aren't repeated here. This file covers what those two missed: LLM-application-specific risk (OWASP's dedicated LLM Top 10, 2025 edition — current, no 2026 edition exists), secrets scanning, supply chain, and output-handling verification.

Same marking key: ✅ already correct · 🔧 real gap, worth fixing · ⏭️ deliberately out of scope, with the reason.

## OWASP Top 10 for LLM Applications (2025) — applicability, reasoned not reflexive

This app's core feature is an LLM answering questions grounded in documents — the LLM Top 10 is the right lens, separate from the general API Top 10 already covered. Full list: LLM01 Prompt Injection, LLM02 Sensitive Information Disclosure, LLM03 Supply Chain, LLM04 Data & Model Poisoning, LLM05 Improper Output Handling, LLM06 Excessive Agency, LLM07 System Prompt Leakage, LLM08 Vector/Embedding Weaknesses, LLM09 Misinformation, LLM10 Unbounded Consumption.

- ⏭️ **LLM01 Prompt Injection — reasoned out, not overlooked.** OWASP's own framing centers this risk on *indirect* injection: instructions smuggled through content the attacker controls but the app trusts (user-uploaded documents, web-fetched pages, tool outputs). This app has none of that vector — the 3 transcripts are static, developer-bundled files, never user-uploaded or fetched from anywhere. Direct injection (a user typing "ignore your instructions" into the chat box) is technically possible but low-consequence: no auth/multi-tenancy to pivot into someone else's data, no tool-calling (LLM06 is N/A for the same reason — no function calling exists), no sensitive data beyond transcripts already served to everyone. Worst realistic outcome is the model going off-topic. Not adding dedicated prompt-injection defenses.
- ⏭️ **LLM02/03/04/08** — don't apply: no fine-tuning, no vector DB/embeddings retrieval, no other users' sensitive data. LLM03 (supply chain) overlaps with dependency scanning, already covered in the backend checklist.
- ✅ **LLM05 Improper Output Handling / LLM09 Misinformation** — already at current best practice. `verify_quote`'s literal substring re-check against source text is exactly what current guidance prescribes ("a citation a reader cannot check is not a control"). Anthropic's Citations API already guarantees `cited_text` is extracted from the literal document provided, so `verify_quote` is defense-in-depth against a mapping bug, not compensating for an untrustworthy API. No further action.
- 🔧 **LLM10 Unbounded Consumption** — this is the one with a genuinely new action, distinct from the app-level rate limiting already planned (backend checklist, §7c): Anthropic's own console supports workspace/per-key **spend limits** (hard-cap monthly spend, returns 429s once hit) and alert thresholds at 50/75/90%. This is a provider-side backstop against a bug or an app-level rate-limit bypass burning real money, and it's not something code can set up — it's a console action only you can take (Settings → Plans & Billing → Spending Limits on platform.claude.com). Recommending it; flagging clearly that it's yours to do, not mine.
- ⏭️ **LLM07 System Prompt Leakage** — low priority, cosmetic-nuisance-level risk at this app's scale (no proprietary system prompt logic worth protecting). Optional: avoid echoing raw provider errors verbatim in user-facing error messages, which the existing `ProviderCallError` handler already does correctly (logs the detail, returns a generic 502 to the client).

## Secrets & supply chain

- 🔧 **Secret scanning in CI (gitleaks)** — public GitHub repos get native secret scanning + push protection automatically at no cost, but a supplementary `gitleaks` CI job (or pre-commit hook) is current baseline for custom patterns and pre-push local feedback. Cheap, worth adding to the CI workflow.
- ⏭️ **SBOM (Software Bill of Materials)** — still framed as compliance/enterprise-driven; recent commentary even argues a committed lockfile already *is* a good-enough SBOM for a project this size. Skipping the formal SBOM pipeline (CycloneDX/SPDX generation) as disproportionate.
- ✅ **Lockfile integrity in CI** — checked `.github/workflows/ci.yml` directly: the frontend job already uses `npm ci` (not `npm install`), enforcing the committed lockfile's hashes. Not a gap — this was miscounted as one earlier in this process, corrected here. The backend gets the equivalent once the `uv` migration (backend checklist) lands and CI switches to `uv sync --frozen`.
- ⏭️ **`security.txt` (RFC 9116)** — implies an ongoing external vulnerability-triage process this case-study project doesn't have; that's the wrong signal to send. A lightweight `SECURITY.md` (GitHub's own community-health file convention) is the proportionate alternative if any signal is wanted at all — optional polish, not baseline, not adding it by default.
